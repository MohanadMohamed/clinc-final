# LAN / TLS deployment plan — Task 7B

These are review templates, not an installer. No Windows settings have been applied. Validate the non-secret plan from the repository root with `python3 -m desktop.packaging.config desktop/packaging/lan.example.toml`. Replace example addresses with clinic reservations. Never put passwords, private-key contents or tokens in this plan.

## Two PCs and one origin

Reserve the doctor NIC's address in the existing router's DHCP configuration; reserve the receptionist separately. Record NIC identity, hostname and addresses in the operator inventory. Use local DNS `doctor.clinic.home.arpa` mapped to the doctor reservation, or identical administrator-managed hosts entries on both PCs when the router cannot provide local DNS. No third application/DNS server is required. Avoid `.local` multicast ambiguity and IP-address URLs. The example `192.168.50.10`/`.11` subnet is illustrative, not a requested network change.

Both clients open `https://doctor.clinic.home.arpa:8443/app/`, including the doctor client. Set `CLINIC_PUBLIC_ORIGIN` to exactly that origin (no trailing slash). The server binds the reserved doctor address. Do not alternate between localhost, IP and DNS names: they are distinct cookie origins and certificates may not cover all of them. The launcher config contains the origin only. Reception runs no backend, database, migrations or development server. No Internet access is needed in ordinary operation.

## PostgreSQL and firewall

Review `postgresql.conf.template` and `pg_hba.conf.template` against the *effective* configuration, including includes, command-line settings and `postgresql.auto.conf`. PostgreSQL listens only on `127.0.0.1,::1`; the backend connection string uses loopback and an application role without superuser/DDL privileges. A separate local migration credential is available only during a deliberate migration. HBA uses SCRAM for explicitly named roles and rejects all other TCP sources. Reconcile local operator administration before applying HBA; do not blindly replace an existing file. No database port is opened to reception. No production DB is created/reset by these templates.

On doctor Windows, preview `Set-ClinicFirewall.ps1 -DoctorAddress 192.168.50.10 -ReceptionAddress 192.168.50.11` (preview is default). After operator review, `-Apply` creates the named rules; `-WhatIf` still suppresses changes. This is not an idempotent installer: existing names fail rather than replace rules. The HTTPS allow rule is restricted to the Private profile, doctor address and receptionist address. The DB inbound block covers all profiles. Require default inbound block and audit existing broad allow rules, VPN/virtual adapters, IPv6 listeners and router port-forwarding separately. Do not disable the firewall or turn an untrusted network Private just to get connectivity. Doctor's own local connection must be tested on Windows. Verify `Get-NetTCPConnection -LocalPort 5432` shows only loopback listeners; reception `Test-NetConnection doctor.clinic.home.arpa -Port 5432` must fail, while HTTPS succeeds.

## Certificate provisioning, trust and rotation

Use a clinic-controlled CA with its signing key offline under operator custody, separate from either workstation. Generate a fresh server key on the doctor host in an ACL-protected directory. Have the CA sign a CSR with the exact DNS SAN in `server-csr.cnf.template`, serverAuth EKU and appropriate key usage; CN alone is insufficient. The CA must preserve/approve the requested SAN/extensions. The certificate chain and key paths are separate; private key and DB configuration are readable only by the service identity and administrators. Never copy the server or CA private key to reception. Distribute only the public CA certificate, verify its fingerprint through a separate trusted channel, and import it into the appropriate Windows trusted-root store for each webview user/service. Do not enable certificate-error bypass flags.

The CSR template can be used with an operator-approved OpenSSL installation: `openssl req -new -newkey rsa:3072 -config server-csr.cnf -keyout server-key.pem -out server.csr` prompts for key protection; unattended service key handling must be resolved with Windows ACLs/secret management before installation. Do not place a decryption password in arguments or XML. No key-generation command is run by this task. Choose certificate lifetime with the operator; monitor expiration at 30/14/7 days and keep both PCs' clocks accurate. Rotate with a new key and matching SAN, verify chain/expiry/key match, stage protected files, then perform a scheduled API restart and health check. Retain the previous valid pair briefly for rollback. For a CA change, install new public trust on both PCs first, rotate the leaf, validate both clients, then remove old trust after the agreed overlap. A compromised key requires immediate replacement, affected-session revocation and trust/revocation response; merely waiting for expiry is insufficient.

## TLS, proxy and sessions

Direct Uvicorn TLS terminates on the doctor PC. `ClinicApi.xml.template` specifies `--no-proxy-headers`; no reverse proxy is part of this design. Untrusted `Forwarded`/`X-Forwarded-*` headers must not determine peer identity, scheme or authorization. Adding a proxy later requires explicit trusted-peer addresses and renewed tests, never a wildcard trust setting. Keep HTTP off the LAN. `/api/health` checks process liveness; `/api/health/ready` performs a DB query and returns sanitized 503 on failure. Readiness does not prove migration compatibility, backups or clinical readiness. Use the trusted-HTTPS `Test-ClinicHttps.ps1` probe; do not log cookies, request bodies, URLs with medical information, or database credentials.

The existing `__Host-clinic_session` cookie is Secure, HttpOnly, SameSite=Strict, Path=/ and has no Domain. Both clients must use the canonical HTTPS origin; server-side role checks and explicit CSRF validation remain authoritative. Obtain a fresh CSRF token after login/session restoration as existing clients do. Pywebview renderer cookie persistence and private-profile behavior must be tested on Windows; logout and account disable must invalidate server sessions regardless of client cache. A stolen unlocked workstation can use an existing session: OS lock, disk encryption, restricted accounts and server expiry mitigate this, while TLS alone does not.

## Reconnection and supervision

Queries may refetch after reconnect. Mutations now explicitly use `retry:false, networkMode:"always"`: offline writes fail immediately instead of being paused for automatic replay. No offline queue is added. A lost response is an *unknown commit outcome*, not proof of failure. Refresh/search the server state before manually resubmitting patient/appointment/visit writes; revision checks and DB overlap constraints remain essential. Billing retries must retain the same idempotency key and identical payload. After reload, reconcile invoices/payments first rather than manufacture a new key for an uncertain action. No notes or tokens are persisted to client storage for replay.

Start PostgreSQL under its own restricted Windows service identity, then start the API service with a dependency on the actual PostgreSQL service name. Dependency running does not prove readiness: poll readiness with bounded backoff (1/2/4/8 seconds, then up to 30 seconds), surface unavailable status, and alert the operator after the chosen timeout. Never run migrations automatically on each service restart. Apply reviewed migrations once during maintenance before starting the matching API version. `ClinicApi.xml.template` is a WinSW-style prototype requiring pinned wrapper/schema validation, absolute path substitutions and explicit Windows service-account setup. It requests two delayed crash restarts, then stops to avoid an infinite crash loop. Liveness failure can trigger supervised restart; DB/readiness failure alone must not trigger destructive repair or a rapid restart loop. Normal shutdown allows in-flight transactions to finish/roll back. After reboot, verify DB listener restrictions, TLS trust, readiness, role access and persistence before opening clients. Resolve sleep/hibernation policy and power/backup procedures with the operator.

## Threat assumptions and Windows acceptance

Assume LAN peers can spoof addresses/DNS or send arbitrary API calls. IP allowlisting reduces exposure but is not authentication; certificate verification and API roles remain required. Assume Windows administrators, the CA custodian and signed/verified installation media are trusted; compromise of those or either unlocked workstation is outside TLS's protection. No public router forwarding, cloud dependencies, or trusted forwarded headers are assumed. Backups and secrets need separate encrypted/offline custody and restore tests. No certification or legal compliance is claimed.

Windows verification is NOT TESTED: PowerShell parser/execution, effective firewall/HBA policy, SCM identity/ACLs/restart behavior, WebView2/pywebview trust and cookies, reboot/sleep, real two-PC DNS/LAN isolation, certificate rotation and expiry. Required Windows gate: clean supported Windows test machines/VMs, installed PostgreSQL and webview runtime, pinned/reviewed service wrapper, synthetic DB, non-production CA, administrator approval and console access for rollback. Record successful HTTPS, rejected wrong-SAN/untrusted/expired certificates, denied DB access from reception, bounded recovery and no duplicate writes after reconnect. No scripts here install a service or alter trust automatically.
