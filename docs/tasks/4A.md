# Sprint 4 Task 4A — doctor-only visits

Date: 2026-10-24. Backend only. Next task: **4B**.

## Contract and boundaries

Migration `0005_visits` adds `visits`, `visit_revisions`, `visit_addenda` and content-free `visit_audit`, separate from administrative `patients` and `appointments`. A visit belongs to one patient and may link to one appointment; a unique appointment reference permits at most one visit per booking. A linked booking must belong to the same active patient and remain scheduled. Once linked, cancellation and rescheduling return 409. Walk-ins have no appointment reference. This does not add arrival/completed appointment states, which Task 3A does not yet support.

Only a doctor can call `/api/visits` routes. `POST /api/visits` creates a draft with optional neurological note, psychiatric note and follow-up plan. `GET /api/visits` lists administrative visit metadata for the doctor; `POST /api/visits/search` searches clinical text in a CSRF-protected request body and returns metadata only, avoiding search terms in URLs. `GET /api/visits/{id}` returns doctor-only content; `GET /api/visits/{id}/history` returns attributed revisions and addenda. `PATCH /api/visits/{id}` requires `expected_revision`, returns 409 on stale edits and only changes a draft. `POST /api/visits/{id}/finalize` requires the current revision and fixes the original text. `POST /api/visits/{id}/addenda` appends attributed corrections without rewriting finalized text. All routes use server-side authentication and doctor authorization; CSRF applies to mutations. Export paths explicitly return 403 to every role until policy is approved.

Each create/edit/finalize stores a full revision with actor and time. PostgreSQL triggers reject UPDATE/DELETE of revisions, addenda and visit audit rows, DELETE of visits, and UPDATE of finalized visits. Ordinary APIs expose no delete or downgrade operation. Audit records actor, event, visit ID and time, never clinical content or search terms. Patient and appointment API schemas remain administrative. Validation errors are generic and SQLAlchemy hides bind parameters. No diagnosis generation, medication advice or decision support was added.

## Retention and open policy

Clinical text and every revision/addendum remain in PostgreSQL and in backups; routine deletion and export are deliberately unavailable. The clinic must approve retention duration, legal correction/deletion process, backup encryption/access, restore testing, operator access and export/print policy before live data. Database ownership or OS administration can override application permissions and triggers, so workstation/database privileges and backups require separate controls. PostgreSQL statement/body logging must stay disabled for clinical payloads. A finalized visit is corrected by addendum only; deciding whether an empty draft may be finalized and how arrival/completion states connect to visits remains a clinic workflow decision. Tests use synthetic records and do not establish clinical compliance or readiness.
