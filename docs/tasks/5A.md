# Sprint 5 Task 5A — billing backend

Date: 2026-10-24. Backend only. Next task: **5B**.

Migration `0006_billing` adds fee versions, invoices, adjustments, cash payments, reversals and metadata-only audit. EGP values are integer piasters; no binary floats or clinical text enter financial schemas. There is no default fee. Doctor sets consultation/follow-up fees with a reason; both roles can read fees, create draft invoices, issue them, record cash payments, read balances and Cairo-day collection summaries. Doctor alone may adjust an issued invoice with a reason, reverse a payment with a reason, or void an invoice after payments are reversed. A posted adjustment cannot reduce total below paid or zero; payments cannot exceed the remaining balance. Financial history rows are append-only in PostgreSQL. Invoice void reason is retained.

`POST /api/billing/invoices` requires a UUID `idempotency_key` and snapshots the active fee. `POST /api/billing/invoices/{id}/payments` and doctor-only `/adjustments` also require keys; repeating the same payload/key returns the existing result, while key reuse with different content returns 409. PostgreSQL uniqueness and invoice row locks prevent duplicate appointments/visits and concurrent overpayment. Invoice state is `draft -> issued -> void`; payment state is derived from immutable cash records and reversals. Appointment cancellation keeps any prior invoice/payment history, blocks new invoice creation for that booking, and blocks issuing or collecting an unlinked invoice after cancellation. It does not silently refund or void an invoice. The daily summary uses Cairo date boundaries and totals recorded cash, reversals and net collection. No gateway, receipt printing, diagnosis display, or frontend work was added.
