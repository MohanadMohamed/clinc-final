# Sprint 3 Task 3A — One-doctor appointments

Backend only. Next task **3B**. The pre-existing AGENTS.md edit is excluded from this checkpoint. No live database or frontend was changed.

## API and business rules

Both doctor and receptionist use the existing server role dependency. Mutations require the existing session, exact Origin and CSRF token. Inputs forbid extra fields; there are no clinical notes, arbitrary statuses or patient reassignment fields.

| Endpoint | Contract |
| --- | --- |
| `POST /api/appointments` | `patient_id`, `kind` (`first_visit` or `follow_up`), explicit `start_at` and `end_at`; creates `scheduled`, returns 201. |
| `GET /api/appointments` | Filters: `patient_id`, `kind`, `status`, aware `start`/`end`; interval filters use overlap with `[start,end)`. Defaults to all statuses, ascending start/UUID order. `page` starts at 1; `page_size` defaults 20, maximum 100. |
| `POST /api/appointments/{id}/reschedule` | Both new timestamps required. Preserves ID/patient/type; only future scheduled reservations may change. Same-slot requests return 400. |
| `POST /api/appointments/{id}/cancel` | Cancels a future scheduled reservation, releases its slot and retains the row/history. Repeated cancellation is 400. |

400: past, wrong duration, reversed/empty interval, invalid filter interval, outside working hours, archived patient, invalid state. 401: anonymous. 403: CSRF/access denial. 404: missing patient/appointment. 409: overlap or patient archive with an upcoming/in-progress reservation. 422: malformed IDs, naive timestamps, unsupported fields/type/status, invalid pagination or invalid Cairo offset. Generic database-unavailable handling remains 503.

Patient archiving and scheduling lock the patient row first; rescheduling/cancelling then lock the appointment row. An archive cannot race successfully with a new booking. Archived patients cannot be booked or rescheduled; cancellation is allowed to release a legacy/operator-created reservation for an archived patient. Past/in-progress reservations cannot be rescheduled/cancelled through these endpoints. Arrival, no-show and encounter completion transitions are future work; only `scheduled` and `cancelled` are accepted at this stage.

## Time policy

Cairo is now explicitly selected by the Task 3A request. PostgreSQL uses `timestamptz` (absolute instants); application DB connections and response timestamps use UTC. Clients supply UTC or an explicit valid `Africa/Cairo` wall-time offset. Naive times are rejected. Non-UTC input must round-trip through Cairo with the same wall clock and offset: skipped spring times fail, while the two autumn occurrences are distinguished by `+03:00` versus `+02:00`. Other zones should submit UTC.

`CLINIC_APPOINTMENT_POLICY` is a validated JSON setting, illustrated in `.env.example`. Development defaults are first visit 30 minutes, follow-up 15 minutes, 09:00–17:00 Cairo, Monday–Thursday and Saturday–Sunday (Friday closed). These defaults require clinic review before deployment. Durations are configurable 5–240 minutes. One same-day working window and a configurable weekday list are supported; split/overnight hours and holidays are not implemented. Restart service workers consistently after configuration changes. Existing reservations are not rewritten when policy changes; new/rescheduled slots must match the current duration. Whole-minute boundaries are required. Durations are elapsed UTC minutes, and both local endpoints must fit one workday with increasing local clock time.

`tzdata==2026.5` is pinned for systems without an IANA database, including Windows. Ubuntu normally uses its system tzdata. Runtime Windows packaging remains untested. Timezone rule changes need a coordinated data update; no network lookup occurs during scheduling.

## Database guarantee and tradeoffs

Migration `0004_appointments` uses:

```sql
EXCLUDE USING gist (tstzrange(start_at, end_at, '[)') WITH &&)
WHERE (status = 'scheduled')
```

A single doctor means there is no resource-equality column; PostgreSQL's built-in range GiST operator class is sufficient and `btree_gist` is unnecessary. The expression constructs a proper timezone-aware range from explicit non-null endpoints. Checks enforce finite, positive intervals, supported types and statuses. The predicate includes all blocking states currently supported and must be updated atomically with future status additions. Cancellation changes the predicate membership, freeing the slot only when its transaction commits. `10:00–10:30` conflicts with `10:15–10:45`, but `10:30–11:00` is adjacent and allowed.

This works across processes and direct SQL writers, without a vulnerable application-level “check then insert.” The constraint may wait on another transaction and raises SQLSTATE `23P01` for a committed conflict; the API rolls back and returns 409. Unlike a global advisory lock, it permits unrelated time ranges to proceed independently. GiST has write/index overhead and is PostgreSQL-specific. The current three-second statement timeout can return generic 503 under prolonged lock contention; clients must refresh before retrying. Policy/archived-patient restrictions are server business rules; database clients are privileged operators and must not bypass them. No production `create_all` or memory booking store is used.

Successful create/reschedule/cancel writes an `appointment_audit` row in the same transaction: actor, appointment, action, prior/new times and database timestamp. A failed conflict rolls back its attempted mutation and success audit. Audit contains no patient narrative. Read APIs expose only administrative projections.

References inspected: [PostgreSQL range constraints](https://www.postgresql.org/docs/current/rangetypes.html#RANGETYPES-CONSTRAINT), [CREATE TABLE exclusion predicates](https://www.postgresql.org/docs/current/sql-createtable.html). These support the database choice; business policy above is this project's decision.
