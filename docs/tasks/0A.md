### Patient registration

**VERIFIED SOURCE:** `MatchingPatients` searches using name/age/gender or nonzero phone/gender and returns patient identity fields ([PatientController, lines 287–329](https://github.com/opensource-emr/hospital-management-emr/blob/99638225ba0876261c2c16c3bd2f9b83f4abbc19/Code/Websites/DanpheEMR/Controllers/Patient/PatientController.cs#L287-L329)). `PostPatient` calls `AddPatient`, which creates an EMPI, timestamps and adds the patient, invokes patient-number generation and returns the patient code/ID ([entry point, 565–574](https://github.com/opensource-emr/hospital-management-emr/blob/99638225ba0876261c2c16c3bd2f9b83f4abbc19/Code/Websites/DanpheEMR/Controllers/Patient/PatientController.cs#L565-L574); [implementation, 2063–2087](https://github.com/opensource-emr/hospital-management-emr/blob/99638225ba0876261c2c16c3bd2f9b83f4abbc19/Code/Websites/DanpheEMR/Controllers/Patient/PatientController.cs#L2063-L2087)). The number-saving helper retries a unique-constraint conflict ([1575–1608](https://github.com/opensource-emr/hospital-management-emr/blob/99638225ba0876261c2c16c3bd2f9b83f4abbc19/Code/Websites/DanpheEMR/Controllers/Patient/PatientController.cs#L1575-L1608)).

**INFERENCE / LIMIT:** Search-before-create is a supported business interpretation; the inspected create path does not itself call the matching endpoint. Mandatory duplicate checking, demographic uniqueness and the exact registration screens were not verified.

**OUR PROPOSAL:** Search/review before registration, immutable clinic identifier, audited demographic correction and no automatic merge on a shared phone number. We do not reproduce its matching algorithm or identifier implementation.

### Appointments

**VERIFIED SOURCE:** `AddAppointment` persists an appointment and converts patient ID zero to null, allowing creation without a registered patient link ([AppointmentController, 1076–1093](https://github.com/opensource-emr/hospital-management-emr/blob/99638225ba0876261c2c16c3bd2f9b83f4abbc19/Code/Websites/DanpheEMR/Controllers/Appointment/AppointmentController.cs#L1076-L1093)). Other methods link a patient, update appointment/provider/status data, and record cancellation actor/time. The `checkedin` branch obtains the patient ID from a linked visit ([1094–1174](https://github.com/opensource-emr/hospital-management-emr/blob/99638225ba0876261c2c16c3bd2f9b83f4abbc19/Code/Websites/DanpheEMR/Controllers/Appointment/AppointmentController.cs#L1094-L1174)). A separate clash helper searches appointments and visits for a patient/provider ([1000–1027](https://github.com/opensource-emr/hospital-management-emr/blob/99638225ba0876261c2c16c3bd2f9b83f4abbc19/Code/Websites/DanpheEMR/Controllers/Appointment/AppointmentController.cs#L1000-L1027)).

**INFERENCE / LIMIT:** These support booking, later identity linkage and arrival/cancellation administration. They do not establish a protected state machine or race-safe slot booking. The clash query uses an appointment-date lower bound and the create method does not invoke it; do not describe it as guaranteed same-day conflict prevention.

**OUR PROPOSAL:** Require an existing patient for bookings, explicitly define transitions and test server-enforced overlap/concurrency rules. This is a deliberate simplification for one doctor.

### Visits

### Billing

**VERIFIED SOURCE:** The active billing routes expose final transactions, provisional billing and provisional payment ([BillingController, 4108–4150](https://github.com/opensource-emr/hospital-management-emr/blob/99638225ba0876261c2c16c3bd2f9b83f4abbc19/Code/Websites/DanpheEMR/Controllers/Billing/BillingController.cs#L4108-L4150)). `NewBillingTransaction` validates deposit availability, optionally creates/maps visit items, calls transaction posting and commits or rolls back ([7990–8053](https://github.com/opensource-emr/hospital-management-emr/blob/99638225ba0876261c2c16c3bd2f9b83f4abbc19/Code/Websites/DanpheEMR/Controllers/Billing/BillingController.cs#L7990-L8053)). `ProcessProvisionalBills` validates deposit availability, posts the bill and derives the billing username from the session ([7093–7152](https://github.com/opensource-emr/hospital-management-emr/blob/99638225ba0876261c2c16c3bd2f9b83f4abbc19/Code/Websites/DanpheEMR/Controllers/Billing/BillingController.cs#L7093-L7152)).

**INFERENCE / LIMIT:** The intended flow can accumulate provisional charges and later bill/pay them. Internal pricing arithmetic, receipt rendering, permissions, idempotency and payment correctness were not verified by this controller inspection.

**OUR PROPOSAL:** Separate invoice/payment/receipt records, authoritative server totals, retry protection and doctor-only corrections. Deposits, external claims and the reference's hospital billing scope are not MVP requirements.
