# Sprint 1 Task 1A — Backend authentication

Date: 2026-10-23. Backend only; frontend unchanged. Next task **1B**. This implements the authentication proposal in [ADR-001](../architecture/ADR-001.md) and the role boundary in the [MVP](../requirements/MVP.md).

## API contract

All responses are `Cache-Control: no-store`. No public registration or account/role editing route exists. Roles are the fixed values `doctor` and `receptionist`, enforced by a database constraint; a partial unique index permits at most one doctor. No patients or clinical routes are added.

| Endpoint | Contract |
| --- | --- |
| `GET /api/auth/csrf` | Creates a five-minute anonymous server session if needed, or rotates CSRF for an existing valid session; returns `csrf_token`. Requires exact configured Origin, or same-origin Referer when Origin is absent. Explicit cross-site Fetch Metadata is rejected. |
| `POST /api/auth/login` | JSON `username`, `password` only. Exact Origin and `X-CSRF-Token` from the anonymous session required. Returns only user id/username/role; rotates session and CSRF on success. Fetch a new CSRF token afterwards. |
| `GET /api/me` | 401 without an active, unexpired authenticated session; returns id/username/role only. |
| `GET /api/auth/session` | Authenticated absolute expiry and idle timeout; no bearer tokens. |
| `POST /api/auth/logout` | Authenticated, exact Origin and current CSRF required; deletes the server session, clears cookie, returns 204. Replay is 401. |

Sessions use a 256-bit random opaque token in a `__Host-clinic_session` cookie: Secure, HttpOnly, SameSite=Strict, Path=/, no Domain. Only SHA-256 token and CSRF digests are stored in PostgreSQL. SHA-256 is used for high-entropy tokens, never passwords. Session expiry is eight hours absolute and thirty minutes idle; requests re-read account role/active status. Disablement rejects and removes the presented session. No signing key, JWT or browser-local-storage token is needed. HTTPS is mandatory for auth cookies even during development; existing loopback HTTP health checks still work.

Argon2id uses argon2-cffi with 64 MiB, three iterations and parallelism four, random salt and rehash-on-login. Unknown usernames use a dummy hash verification; responses do not reveal whether the username exists. Usernames are ASCII identifiers normalized to lowercase; displayed Arabic personal names are outside this task. Bootstrap passwords must be 15–128 characters with no truncation. Passwords are SecretStr inputs; validation errors return generic 422 without echoing input. Login bodies are limited to 8 KiB before JSON parsing, including chunked requests. Database errors return sanitized 503.

## Authorization pattern

Use `Annotated[User, Depends(require_role("doctor"))]` on doctor-only endpoints, or explicitly allow both roles. `require_user` revalidates session/account and applies Origin plus synchronizer-token checks to unsafe methods; `require_role` returns 403 for an authenticated wrong role. Always apply this dependency to later protected routers/routes; it does not replace object/field authorization. Test-only routes exercise doctor access and protected mutations; they are not mounted in the live application.

## Throttling and audit

PostgreSQL stores hashed account/IP bucket identifiers. Transaction advisory locks serialize buckets across application workers; tests exercise simultaneous requests. In each fifteen-minute fixed window: at most five login attempts per normalized account, thirty per peer IP, and sixty CSRF retrievals per IP. Both successful and failed login attempts count, and login success does not reset limits. Missing/invalid CSRF is rejected before password verification. 429 includes Retry-After: 900 (conservative whole-window delay). Forwarded headers are not used by application code; run Uvicorn with `--no-proxy-headers` for the direct TLS deployment so attacker-controlled forwarded headers cannot change peer identity.

Audit records contain event, timestamp and optional actor UUID only: bootstrap, successful/failed login, throttling, expiration, authentication/authorization denial, CSRF denial and logout. No username, password, cookie, CSRF token, request body, medical content or raw IP is written to audit. There is no API to alter audit records. Database errors cannot produce a durable audit while the database is unavailable. Operational retention/cleanup of expired session/throttle rows and audit retention remain to be scheduled before deployment; no destructive cleanup is included here. Account-based throttling can temporarily delay legitimate users under attack; access resumes after the window. These LAN controls are not protection against arbitrary network-volume denial of service.

## Secrets, migrations and local bootstrap

Install backend dependencies and apply migrations only to the intended dedicated database:

```bash
cd backend
.venv/bin/python -m pip install -r requirements.txt
.venv/bin/alembic upgrade head
.venv/bin/alembic current
.venv/bin/python -m app.bootstrap --username doctor
```

The last command requires a local interactive terminal and prompts twice with getpass. There is no password command-line argument, stdin-pipe mode, default password or HTTP bootstrap route. Use a unique strong password; never put it in history, fixtures, logs or screenshots. One transaction creates the doctor and persistent bootstrap sentinel plus audit event under a PostgreSQL advisory lock. Re-running is rejected, even if later provisioning logic changes. Recovery is an authorized local operator procedure, not a reset endpoint.

The CLI connects with `CLINIC_DATABASE_URL`; for bootstrap only, supply a locally authorized operator account through protected configuration. Restore the least-privilege application configuration before starting the service. `.env` stays untracked and is never displayed. `CLINIC_MIGRATION_DATABASE_URL` remains migration-only. Set `CLINIC_PUBLIC_ORIGIN` to the exact bare HTTPS origin, including port when non-default; default is `https://clinic.local`. Plain HTTP, URL credentials, paths, fragments and query strings are rejected. The TLS hostname and trust must match; do not bypass certificate checks.

After migrations, the database owner can grant the existing application role these permissions (substitute the locally provisioned role name):

```sql
GRANT USAGE ON SCHEMA public TO clinic_dev_app;
GRANT SELECT, INSERT, UPDATE ON users TO clinic_dev_app;
GRANT SELECT, INSERT, UPDATE, DELETE ON login_sessions, auth_throttles TO clinic_dev_app;
GRANT INSERT ON auth_audit TO clinic_dev_app;
```

Do not grant the ordinary application role access to `auth_bootstrap`, audit modification/deletion, schema ownership or superuser privileges. Bootstrap uses the operator role. No receptionist provisioning endpoint is included in 1A; tests create synthetic accounts directly in their private cluster. Account-management scope belongs to a future task.

For local HTTPS development after generating trusted local certificates outside the repo:

```bash
cd backend
.venv/bin/uvicorn app.main:app --host 127.0.0.1 --port 8443 --ssl-certfile /path/to/local-cert.pem --ssl-keyfile /path/to/local-key.pem --no-access-log --no-proxy-headers
```

Set the origin accordingly in protected configuration. This is a run command template, not a claim that TLS or Windows was tested. Frontend remains untouched and has no login flow yet. Tokens returned by the future login client must stay in memory and never be persisted or logged.

## Verification

Run from `backend/`:

```bash
.venv/bin/pytest -q
.venv/bin/ruff check .
.venv/bin/ruff format --check .
.venv/bin/pip check
```

The auth fixture always initializes a new private socket-only PostgreSQL cluster; it never uses a configured existing DB. It executes `upgrade head`, `check`, `downgrade 0001_baseline`, `upgrade head`, `check` before the tests. Truncation occurs only within that fixture-owned disposable cluster between tests. It stops the cluster at teardown. Tests use random synthetic passwords and no patient data.

Results are recorded in [STATUS](../STATUS.md). HTTPX TestClient exercises HTTPS cookie behavior and real SQL; it is not a real-browser/TLS/network test.
