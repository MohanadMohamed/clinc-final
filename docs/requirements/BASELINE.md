# Confirmed project-wide product baseline

Confirmed by the user on 2026-10-23. These decisions govern every task. Earlier documents and task plans must be reconciled with them; a draft implementation choice is not an additional confirmed product requirement.

1. **Product:** Arabic RTL, single-doctor neurology and psychiatry clinic. Separate doctor and receptionist accounts; optionally more named receptionist users later. One doctor remains the scope.
2. **Deployment:** Two Windows PCs, no third server. The doctor PC runs FastAPI and PostgreSQL as Windows services and the doctor desktop client. The receptionist PC runs the desktop client only. One central PostgreSQL database, LAN-only HTTPS, no Internet needed in normal operation. Loss of Internet must not disable ordinary work; loss of the doctor server does not imply offline write support.
3. **Development/build boundary:** Ubuntu is the development machine. Build and test Windows packages on Windows: physical hardware, a VM or a Windows CI runner. Ubuntu results cannot establish Windows package acceptance. External publishing or deployment still requires permission.
4. **Backend:** Python, FastAPI, SQLAlchemy 2, PostgreSQL, Alembic, Pydantic, pytest and HTTPX.
5. **Frontend:** React, TypeScript, Vite, Tailwind CSS, shadcn/ui, React Router, TanStack Query, React Hook Form and Zod. Tests use Vitest, Testing Library and Playwright.
6. **Desktop:** pywebview thin launcher. Windows packages use PyInstaller plus selected Windows installer tooling. The installer tool, service wrapper and webview runtime provisioning remain to be selected and tested. The launcher must preserve server authorization and trusted HTTPS; it contains no database or clinical business logic.
7. **Architecture:** Modular monolith, with `backend/app/{api,core,models,schemas,repositories,services}`, `frontend/`, `desktop/`, `tests/` as appropriate and `docs/`. No microservices or extra application server machine.
8. **Permissions:** Doctor reads/edits authorized clinical notes. Reception handles administrative patients, appointments and permitted billing. Reception cannot access clinical or psychiatric notes through UI, direct API, search, print or error responses. FastAPI checks permissions on each route; account role is independent of the PC used.
9. **Data:** Synthetic patients only in development. Avoid credentials and medical information in logs, screenshots, fixtures and client storage; use minimal synthetic content only where a test requires it. Never infer clinical compliance or clinical readiness from technical checks.
10. **References:** [hospital-management-emr](https://github.com/opensource-emr/hospital-management-emr) is a workflow study reference. [morluto/rea](https://github.com/morluto/rea) is optional only after security review and must never be a runtime dependency. Study architecture/business rules, do not blindly copy code/assets, and respect original and third-party licenses. The optional repository has not been reviewed or approved for use.
11. **Git and operations:** Commit or create an explicit clean checkpoint per task. Preserve pre-existing edits. Do not destroy/reset databases, discard work or publish externally without permission. Use versioned Alembic migrations and report actual PASS/FAIL/NOT TESTED evidence.
